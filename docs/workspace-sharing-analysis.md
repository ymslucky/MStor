# 空间共享设计评估

> 问题：当前的「空间共享」设计是否合理？是否应该完全隔离？
> 结论（2026-10-23 已确认）：MStor 收敛为个人云盘。共享空间不再是产品能力，仅保留公开分享；设置页移除成员入口，侧栏移除空间切换。
> 原分析保留作为决策记录。

## 1. 当前模型

MStor 现在是三层能力混在一起：

1. **个人空间**：每个用户首登自动建一个 workspace，自己是 owner；
2. **空间成员**：通过邀请把其他人加入同一个 workspace，角色 owner/admin/member；
3. **公开分享**：为节点生成 token 链接，可设密码/有效期/下载次数。

前两者是「空间共享」，第三个是「外链分享」。它们解决的是不同问题，但 UI 上都叫“共享”，容易让用户以为是一件事。

## 2. 完全隔离的利与弊

### 利

- 权限模型退化为「一个用户一个空间」，不需要成员、邀请、角色；
- 不会出现跨用户数据泄露、越权邀请、最后一名 owner 等边界情况；
- 对个人云盘/单用户场景更简单，设置页与导航也更短。

### 弊

- 失去「家庭共享空间」这一核心场景；
- 用户之间无法协作，只能靠公开链接；
- 管理员 act-as 变成唯一的跨空间通道，不适合正常家庭使用；
- 以后要恢复共享，需要重新引入数据模型和迁移。

## 3. 早期推荐（已被最终决策取代）

保留共享能力，但把它从“默认路径”改为“显式选择”：

- 每个用户注册后只有**私有个人空间**，默认不加入任何共享空间；
- 需要家庭/团队协作时，由 owner 显式创建「共享空间」并邀请成员；
- 「成员」页只在共享空间出现；
- 公开分享链接独立于空间共享，始终可撤销/过期；
- 设置页提供平台级开关：
  - 允许空间共享（默认关闭或由管理员开启）；
  - 允许公开分享；
  - 新用户默认额度（已做：1GB）。

这样既保留家庭场景，又让单用户默认处于完全隔离状态。

## 4. 当前需要修的 UX 问题

1. 个人空间与共享空间的视觉/文案没有区分；
2. 「成员」入口对个人空间也出现，容易误导；
3. 邀请链接与公开分享链接都叫“分享”，语义混淆；
4. 最后一个 owner、邀请认领等规则对普通用户过于复杂；
5. 没有平台级“禁止共享/禁止外链”的总开关。

## 5. 最终落地（2026-10-23）

1. 设置页移除「成员」入口；侧栏/移动抽屉移除空间切换；
2. 每个用户一个私有空间；保留公开外链分享；
3. 成员/邀请 API 与 invitations 表已删除；memberships 仅保留个人空间 owner 关系；
4. 管理员通过 act-as 排障，不再作为正常家庭协作通道。
